# 今日の夕食

平日19時台の「今日の夕食どうする」を、**1往復で終わらせる**アプリ。

---

## 課題（実データ）

対象は私の妻。架空の属性は足していない。

昨日のLINE履歴：**19:18〜19:20 の約2分間に22通**。

決着が長引く原因は、意欲でも段取りでもなく **判断材料が夫と妻に分かれていて、どちらも全体を見ていないこと**。

しかも子どもは2歳。「もう限界」に交渉の猶予がない。

| 材料 | 持っている人 | 昨日どうだったか |
|---|---|---|
| 米を炊いたか | 夫 | 炊き忘れていた |
| 子（2歳）の空腹度 | 妻 | もう限界 |
| 冷蔵庫の残り物（おにぎり弁当） | 妻 | **20通目付近でようやく出てきた** |
| 寄り道して買えるか | 夫 | 寄れた |

決定打（冷蔵庫の残り物）が最後まで出てこないので、20往復してから
「じゃあそれで」になる。確認できた直近2日とも「ごはん」が問題になっていた。

---

## 解き方

**4つ全部は聞かない。決着に必要な情報だけを求める。**

20往復の原因は「何を聞けば終わるのか誰も知らない」こと。だから未回答の項目に
あり得る値を全部入れて結論を出し直し、

- **結論が1つに収束していれば、残りを聞かずに決める**
  （例：残り物あり＋もう限界 → 米と寄り道は結論を変えないので聞かない）
- **まだ割れていれば、候補を最も減らす1項目だけを名指しする**
  （「これを聞けば決まります：妻・冷蔵庫の残り物」）

組み合わせは最大 `2×3×2×2 = 24` 通りなので、全探索で足りる。

状態はURLに入っているので、**そのままLINEに貼れば相手の画面に自分の入力が出る**。

カレンダー共有アプリでは解けない。これは予定ではなく、
在庫・空腹・位置を統合する「その日の意思決定」だから。

---

## AIの役割

AIは**決定しない**。決定はルール（`lib/decide.ts`）が行う。

```
自由文    ──[LLM · 実行時]──▶ 4項目 ──[ルール]──▶ 結論 ──[表]──▶ 一文
レシート  ──[LLM · 実行時]──▶ 材料               非決定要素はここまで  ↑
                                          ビルド時にLLMで生成し固定 ──┘
```

LLMがいるのは**入口だけ**。どちらが外れても、4項目を手で選べば結論は出る。

### 出口は実行時にLLMを呼ばない

入力の組み合わせは24通り、結論は7通りしかない。毎回LLMを呼ぶ理由がないので、
`scripts/build-sentences.mjs` で7件を一度だけ生成し、レビューして
`lib/sentences.json` にコミットしてある。実行時は表を引くだけ。

> 今夜は冷蔵庫の残り物で食べます。私が残り物を出すので、買い物せずまっすぐ帰ってきてください。

**同じ結論なら常に同じ一文。** 「昨日と言い方が違う」が起きない。
`lib/decide.ts` の文言を変えるとキーが変わり、表が欠けてテストが落ちるので、
再生成を忘れたまま本番へは出ない。

再生成:

```bash
node --experimental-strip-types scripts/build-sentences.mjs
```

### 入口は決定的にできない

自由文が入力なので事前生成できない。ここだけ実行時にLLMを呼ぶ。ただし
出力は必ず `normalizeParsed` を通り、想定外の値は `null` に落ちてトグルが
未選択のまま残る。**読み取りが外れても不正な状態にはならないし、手で選び直せる。**

`/api/parse` にはレート制限がある。1クライアントあたり8回/分、
全体で120回/時。超えると 429 と `retry-after` を返し、画面は
「読み取りの回数制限に達しました。少し待つか、下から選んでください」と出す。

## 判断ルール

| 条件 | 結論 |
|---|---|
| 残り物あり ＋（すぐ食べたい or 米なし） | 冷蔵庫の残り物で食べる |
| 米あり | 家のごはん（急ぎでなく寄れるならおかず1品だけ買う） |
| 米なし ＋ 寄り道できる | 夫が買って帰る |
| 米なし ＋ 残り物なし ＋ 寄れない | 出前をとる |

「残り物が最優先」は昨日の実データから来ている。いま出せるものが家にあるなら、
それが最速で、20往復する理由がない。

## 構成

```
lib/decide.ts             判断ロジックと問い合わせ層（純粋関数）
lib/sentence.ts           結論 → 固定の一文（表を引くだけ）
lib/sentences.json        事前生成した7件（レビュー済み・コミット対象）
lib/rate-limit.ts         スライディングウィンドウのレート制限
lib/receipt.ts            レシート読み取り結果の正規化
lib/image.ts              写真の縮小（canvas）
app/page.tsx              URLを読む Server Component
app/dinner-decider.tsx    画面本体
app/api/parse/route.ts    自由文の読み取り（実行時LLM）
app/api/receipt/route.ts  レシート画像の読み取り（実行時LLM）
scripts/build-sentences.mjs  一文の再生成（開発時のみ）
```

テストは77件。`lib/*.test.ts` と `__tests__/` に同居。

Next.js 16 App Router / React 19 / TypeScript / Tailwind CSS v4 / Vitest /
Anthropic SDK。自由文は `claude-opus-5`、レシートは `claude-haiku-4-5`
（決まった形を抜くだけなので Haiku。単価は Opus 5 の5分の1）。

DBなし、認証なし、リアルタイム同期なし、UIライブラリなし、状態管理なし。
**URLが共有状態そのもの。**

## レシート読み取り

夕食の判断は「材料があるか」「できている料理があるか」「ごはんが炊けているか」で決まる。
在庫管理アプリは誰も入力しないので、入力コストがゼロに近い手段から着手した。

レシートを撮ると、材料が読み取った中身に入れ替わる（`claude-haiku-4-5`、0.45円/回）。
写真はブラウザ側で長辺1568pxに縮めてから送る。

**埋まるのは3つのうち材料だけ。** レシートは買ったものしか写しておらず、
何を作って何が残っているかを知らない。だから決定打の「できている料理」には繋いでいない。
嘘の在庫で夕食が決まるのは、何も出さないより悪い。

読み取りは外すことがある（品目の欠落、まれに存在しない品目）。
チップは×で1つずつ消せる。デモでは `?demo=1` を使う。

---

## 今日作らなかったもの

- **音声で買ったものを登録** — レシートは実装した。音声はまだ。静的なモックだけ置いてある。

- **できている料理の自動登録** — 決定打はここだが、レシートには写らない。埋める手段がない。

## これから

- 残り物を「あるか」ではなく「何があるか」まで持つ（昨日の決定打はおにぎりだった）
- 帰宅時刻の実測を夫の位置から自動で入れ、`寄り道できるか` を聞かずに埋める
- 決まった結論の履歴から、翌週の米を炊く判断を先回りする
